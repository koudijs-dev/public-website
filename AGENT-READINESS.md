# Agent readiness: what is done, what is open

This site should be easy for crawlers, language models, and agents to read. It is a
public personal site; the whole point is to be found and quoted. So the default answer
to "may I read this?" is yes, and it should be stated out loud rather than left to be
inferred.

This file records what is in place, what is still open, and why the open items are
blocked on hosting decisions rather than on writing code.

## Background: two problems, stacked

An agent-readiness scan reported `robots.txt exists but appears invalid (no User-agent
directive)`. That turned out to be two separate faults sitting on top of each other.

**1. Hugo was never publishing a robots.txt.** `layouts/robots.txt` has been in this
repo for a long time, but Hugo only renders it when `enableRobotsTXT` is set, and it
was not. The template was dead code. The `gh-pages` branch contained no `robots.txt`
at all — confirmed with `git ls-tree origin/gh-pages`.

**2. Cloudflare answered in our place.** With nothing at the origin, the edge served
its own file: the Content Signals legal preamble and nothing else. Twenty-odd lines of
comments explaining what content signals mean, followed by no `User-agent` line, no
`Allow`, no `Disallow`, and no actual signal. Not a valid robots.txt, and not something
anyone here wrote. Meanwhile Cloudflare's managed bot preferences were blocking AI
crawlers by a default nobody chose.

Both are now fixed: `enableRobotsTXT: true` in `config.yml`, and Bot Preference Sync
disabled at the edge so the origin's file is the one that gets served.

The lesson worth keeping: an empty origin is not a neutral origin. Something else will
fill the gap and speak on your behalf, and what it says may not be what you would have
said — or even be valid.

## Done (in this repo)

| What | Where |
| --- | --- |
| `enableRobotsTXT`, so Hugo actually emits the file | `config.yml` |
| `robots.txt` — everyone allowed, Content Signals `search=yes, ai-input=yes, ai-train=yes` | `layouts/robots.txt` |
| Named AI crawler groups repeating the same permissive rules | `layouts/robots.txt` |
| `llms.txt`, generated from the site's own pages and posts | `config.yml` (`outputFormats.LLMS`) + `layouts/_default/index.llms.txt` |
| ARD capability manifest | `static/.well-known/ai-catalog.json` |
| `<link rel="sitemap">` and `<link rel="alternate">` to `llms.txt` | `layouts/partials/extend_head.html` |

Two things worth knowing about how this is wired:

- A crawler that matches one of the named groups in `robots.txt` ignores the wildcard
  group entirely (RFC 9309), which is why the permissive rules are repeated rather
  than inherited.
- `llms.txt` ranges over `.Site.RegularPages`, so new posts and pages appear in it
  automatically. Nothing to remember on publish. The sitemap was already generated by
  Hugo and was the one thing the scan did not complain about.

## Open: blocked on the hosting setup

These need control over HTTP response headers or DNS. Production publishes to
`gh-pages` (`.github/workflows/publish-stuff.yml`), and GitHub Pages serves static
files without letting us set headers.

Note the irony: this repo *already contains* an nginx config and a Dockerfile
(`nginx/default.conf`), but only for per-PR preview environments. The preview stack can
set response headers; production cannot.

### 1. `Link` response headers (RFC 8288)

Agents look for discovery hints in headers, not just in HTML. The homepage should send
something like:

```
Link: </llms.txt>; rel="alternate"; type="text/plain",
      </sitemap.xml>; rel="sitemap",
      </.well-known/ai-catalog.json>; rel="service-desc"
```

The `<link>` tags in `extend_head.html` are the in-page equivalent and cover agents
that parse HTML, but header-based checks will not see them.

*Blocked by:* no header control on GitHub Pages. Three lines of `add_header` in
`nginx/default.conf` the moment production runs that container.

### 2. Markdown for Agents

Requests sending `Accept: text/markdown` should get markdown back, with HTML staying
the default for browsers. Verified as not happening today.

This site is a particularly silly place to be missing it, because everything in
`content/` *is already markdown*. We render it to HTML at build time and then have no
way to hand back the source. Hugo can emit a markdown output format alongside HTML
without much trouble; what is missing is the content negotiation, which is a server
concern.

*Blocked by:* a Cloudflare feature on this account, where an origin we run could do the
negotiation directly against markdown we already have.

### 3. DNS for AI Discovery (DNS-AID)

SVCB/HTTPS records under `_index._agents.koudijs.dev` pointing at the discovery
documents, with DNSSEC on the zone.

*Blocked by:* nothing expensive — this is DNS and is achievable wherever the zone
lives. Parked because the spec is still an IETF draft
(`draft-mozleywilliams-dnsop-dnsaid`) and it is the lowest-value item here.

### 4. Check what the edge blocks

Independently of `robots.txt`: if any managed AI-bot blocking is still active in
Cloudflare's AI Crawl Control, it overrides our permissive rules at the edge and a
crawler never reaches the origin to read the welcome. Re-verify after any change to the
proxy setup.

## Observation: previews are crawlable

`layouts/robots.txt` has a guard meant to serve `Disallow: /` for non-production
builds. It cannot currently fire: the condition is
`hugo.IsProduction | or (eq .Site.Params.env "production")`, and `params.env` is
hardcoded to `production` in `config.yml`, so the production branch always wins.
Preview builds at `pr<N>.preview.koudijs.dev` therefore serve the permissive rules.

This predates the changes here and the risk is low, since preview URLs are not linked
from anywhere. Left alone deliberately, because the obvious fix — setting
`HUGO_PARAMS_env: development` in `preview-image.yml` — would also switch off
OpenGraph, analytics, and schema.org output in previews, making them a less faithful
copy of production. If it is worth fixing, the cleaner route is to set
`HUGO_ENVIRONMENT: development` for previews and drop the `params.env` half of the
condition, so `hugo.IsProduction` alone decides.

## Not applicable

Several agent-readiness checks assume a site with an API behind it. This is a personal
site and blog, so these are deliberately absent rather than missing:

- `/.well-known/api-catalog` (RFC 9727)
- `/.well-known/openid-configuration`, `/.well-known/oauth-authorization-server`
- `/.well-known/oauth-protected-resource` (RFC 9728)
- `auth.md`
- `/.well-known/mcp/server-card.json`
- `/.well-known/agent-skills/index.json` — no skills to publish
- WebMCP tools

Publishing empty versions of these would satisfy a checker while pointing agents at
nothing, which is worse than not publishing them.

## The direction

The intent is to move the public sites onto our own cluster and stop depending on
GitHub Pages. Cloudflare may stay as a proxy, or go entirely. Either way, once there is
an origin we control:

- `Link` headers become a few lines of nginx config — in a file this repo already has.
- Markdown content negotiation becomes part of the build, using markdown that is
  already sitting in `content/`.
- Nothing about discovery is gated behind someone else's pricing tier, or their default
  opinion about who may read this.

## How to verify

```sh
curl -sS https://koudijs.dev/robots.txt
curl -sS https://koudijs.dev/llms.txt
curl -sS https://koudijs.dev/sitemap.xml
curl -sS https://koudijs.dev/.well-known/ai-catalog.json | python3 -m json.tool
curl -sS -D - -o /dev/null https://koudijs.dev/ | grep -i '^link:'
curl -sS -D - -o /dev/null -H 'Accept: text/markdown' https://koudijs.dev/ | grep -i '^content-type:'
```

The last two are the open items: today they return nothing and `text/html`.

Locally, `hugo --minify` writes all of the above into `public/`. To check the preview
branch of the robots template: `hugo -e development --minify` with
`HUGO_PARAMS_env=development`.
